# Выпуски SirusChatWheel

Исходники и все общие звуки хранятся в Git. Для игроков GitHub Release содержит один готовый `SirusChatWheel-X.Y.Z.zip`, который устанавливается копированием в AddOns. Каталог и кэш создаются при сборке и не требуют действий от игрока.

Начиная с 1.5.1, в игровом ZIP только одна рабочая копия звука — в `Media/Cache`. Авторские `Sounds`, `SoundNames.json`, `Update-Sounds.cmd` и `Watch-Sounds.cmd` остаются в исходниках. Сборщик использует их во временной папке, а в ZIP их не добавляет. `ReleaseInfo.json` обозначает готовый выпуск и блокирует случайную пересборку из старых файлов после копирования поверх.

Для перехода со старого архива с дублями нужно один раз заменить папку аддона целиком: копирование поверх не удаляет старый `Sounds`. Настройки в `WTF` сохраняются. Исходники автора при этом остаются отдельно в репозитории.

1. Внесите изменения. Новые звуки положите в `SirusChatWheel/Sounds`, подписи — в `SirusChatWheel/SoundNames.json`. Не переименовывайте старые файлы, если хотите сохранить назначения секторов.
2. Измените версию одновременно в `Core.lua` и `SirusChatWheel.toc`. Обновите `RELEASE_NOTES.md` с правильным именем ZIP и описание изменений в `README_RU.txt`. Сохраните изменения коммитом в GitHub Desktop.
3. В History нажмите правой кнопкой на этот коммит → Create Tag. Название — `vX.Y.Z`, например `v1.4.0`. Затем нажмите Push origin.

GitHub Desktop отправляет аннотированный тег вместе с коммитом. Процесс **Release** на вкладке **Actions** проверяет совпадение версии, запускает проверки Lua/PowerShell, собирает полный архив и публикует Release с этим архивом. Отдельный токен в настройках не требуется: используется служебный токен GitHub Actions.

Проверьте зелёное завершение Actions и наличие полного ZIP в Releases. Если процесс завершился ошибкой, откройте упавший шаг: релиз может остаться черновиком, его нельзя считать опубликованным. Не передвигайте уже опубликованные теги и не заменяйте содержимое выпущенного архива — исправление получает новую версию.

Если отправка тега не запустила процесс, откройте Actions → Release → Run workflow, оставьте ветку main и в поле tag укажите существующий тег, например v1.4.0. Будут взяты исходники именно этого тега. Запуск требует отсутствия Release с таким тегом: существующий выпуск автоматически не перезаписывается.

Для локальной проверки нужны Windows, Python 3.13 и `lupa==2.8` (`python -m pip install lupa==2.8`). Выполните `python tests/validate.py`, затем `python tools/build_release.py`. Готовый ZIP будет в `dist`.

Нумерация: **X** — несовместимое изменение; **Y** — новая функция, запись или фраза; **Z** — исправление. После увеличения старшего числа младшие сбрасываются в ноль.
